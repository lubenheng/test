# IIC Tool v6 代码架构分析报告

> 分析对象：`IICtool_v6/`（当前活跃版本，15 个 Python 文件，约 3200 行）
> 分析日期：2026-10-14
> 分析范围：模块分层、调用关系、2361 协议实现、MTP 数据模型、代码质量与仓库卫生

---

## 一、结论摘要

| 维度 | 评价 |
|---|---|
| 分层设计 | **良好**。GUI → 业务 → 器件 → 通信 → DLL 五层单向依赖，回调注入解耦彻底 |
| 协议实现 | **可用但脆弱**。硬编码时序、魔法值多，地址模型有两处不自洽 |
| 错误处理 | **偏弱**。关键路径存在"静默吞异常"，失败被呈现为成功或数据 0 |
| 并发模型 | **有缺陷**。后台线程直接操作 Tk 控件；超时后遗留线程与总线恢复竞争 |
| 死代码 | **较多**。约 8 个模块级函数、1 个类方法、2 个属性无任何调用者 |
| 仓库卫生 | **需整改**。`.env` 凭据已入库；2034 个二进制文件入库；`.git` 163MB |
| 测试 | **缺失**。无测试框架、无 CI，`CRC_Test.py` 是独立脚本 |

**最高优先级 3 项**：`.env` 凭据泄露、两套 CRC-32 算法并存且结果不同、MTP 使能失败被静默吞掉。

### 3.2 模块职责与关键接口

#### `IICtool.py` — GUI 总控（807 行，最大单点）

`class I2CGUI` 不是 `tk.Tk` 子类，而是持有 `root` 引用的普通类（`IICtool.py:17-18`）。

| 关键成员 | 说明 |
|---|---|
| `self.i2c` / `self.mtp` | 通信控制器 / MTP 器件层实例 |
| `self.log_records` | 结构化日志缓存（导出 Excel 用） |
| `self.quick_rows` | 5 行快速操作区的 30 个 `StringVar` |
| `log()` / `update_status()` | 同时写 Tk Text 与 `log_records` |
| `_do_write` / `_do_read` | **注入给业务层的回调**（`IICtool.py:211-215`） |

#### `i2c_comm.py` — 通信层（743 行）

DLL 原型通过 `_ensure_dll_ready` 一次性声明（`i2c_comm.py:90-194`）。实际投入使用的 DLL 函数仅 6 个：`OpenUsb`、`CloseUsb`、`ConfigIICParam`、`IICSendData`、`IICSendAndRcvData`、`PWMOut`。其余（`IICRcvData`、全部 SPI、全部 InternalList、`PWMClose`、`IOSetAndRead`）声明了但主流程未用。

关键常量：`baudrate=921600`、`pwm_base_clock=48000000`、`read_timeout_ms=20`。

#### `iic_ops.py` — 2361 协议 + IIC 批量（507 行）

- 模块级：`build_iic_payload()`（报文编码）、`execute_write()`、`execute_read()`
- `IICLogic`：仅作静态命名空间使用（解析、Excel 模板、批量执行）

#### `mtp_ops.py` — MTP 器件层（96 行）

把 MTP 字节地址翻译成 `(ADDR, INDEX)` 寄存器对，并把操作翻译为命令码写入。

| 操作 | 命令码 | 写入位置 |
|---|---|---|
| 读触发 | `0x200` | 目标 `(addr, index)` |
| 烧录 | `0x400 \| byte` | 目标 `(addr, index)`，**写 2 遍** |
| 扇区擦除 | `0x800` | 扇区首地址 |
| 全片擦除 | `0x1000` | `(0, 0)` |

#### `mtp_batch_ops.py` — MTP 批量（553 行，全静态）

`MTPBatchLogic` 不持有任何 GUI/硬件对象，只接收 `mtp_ctrl` 与回调，因此可脱离 GUI 复用。这是整个代码库设计最干净的部分。

## 四、核心数据模型

### 4.1 2361 寄存器报文

```
写帧 (7 字节):  [0x25] [HDR_H] [HDR_L] [D0] [D1] [D2] [D3]
读帧 (两阶段):
   阶段1  START → [0x25] [HDR_H] [HDR_L] → STOP
   阶段2  START → [0xA5] → 收 4 字节 → ACK → STOP

HDR(16bit) = [RW(3)] [ADDR_rev(5)] [INDEX_rev(6)] [00(2)]
    RW: read=0b110, write=0b010
    ADDR_rev  = ADDR 的 5 位比特反转
    INDEX_rev = INDEX 的 6 位比特反转
数据: 32 位整体比特反转后发送（收发对称）
```

实现见 [iic_ops.py:25-56](IICtool_v6/iic_ops.py#L25-L56)（编码）、[iic_ops.py:88-129](IICtool_v6/iic_ops.py#L88-L129)（读回解反转）、[i2c_comm.py:634-672](IICtool_v6/i2c_comm.py#L634-L672)（两阶段时序）。

### 4.2 MTP 地址模型 — 存在两套并存且不自洽

**模型 A（字节粒度）**，用于单字节烧录/读取：

```python
# mtp_ops.py:14-17
addr  = (mtp_byte_addr >> 6) & 0x1F     # 每 64 字节换一个 ADDR
index =  mtp_byte_addr       & 0x3F     # 每字节递增 INDEX
```

**模型 B（Word 粒度）**，用于 Excel 模板与批量烧录：

```python
# mtp_batch_ops.py:191, 331, 141
phys_addr = ADDR(基地址) + INDEX(Word偏移) * 4     # 每个 INDEX 覆盖 4 字节
```

两者对同一物理地址给出**不同的 INDEX**：物理字节地址 4 → 模型 A 得 `(0, 4)`，模型 B 得 `(0, 1)`。

> **风险**：`read_and_export_mtp_sector()` 在导出时用模型 A 的结果伪装成模型 B 的列。见问题 **P1-4**。

### 4.3 CRC-32 — 两套算法并存且结果不同

| 位置 | 算法 | 用途 |
|---|---|---|
| [crc.py:7-25](IICtool_v6/crc.py#L7-L25) | **LSB 优先**（逐字节取 bit0→bit7，反馈 CRC 的 MSB） | 全片烧录时计算写入值 |
| [mtp_batch_ops.py:526-533](IICtool_v6/mtp_batch_ops.py#L526-L533) | **MSB 优先**（内联循环，标准 CRC-32/MPEG-2 形式） | 「读出MTP并导出」的 `CALCULATED` 行 |

两者多项式同为 `0x04C11DB7`、初值同为 `0xFFFFFFFF`，但**输出恒不相同**。实测（同机、同输入）：

```
n=  1  LSB=DFA9323A  MSB=698AB91F
n=  4  LSB=B6EDE334  MSB=85E13510
n=312  LSB=7E4F00E5  MSB=6FBBA47A   ← 全片数据长度
```

**后果**：烧录写入的 CRC 由 LSB 算法产生，而读回自检的 `CALCULATED` 由 MSB 算法产生。用「读出MTP并导出」的结果去比对烧录是否正确，**永远对不上**，且差异与数据无关、无法通过调整模板规避。详见问题 **P0-2**。

## 六、问题清单

严重度定义：**P0** 造成错误结论或安全风险；**P1** 导致功能不可靠或数据错误；**P2** 质量与可维护性。

### P0-1 `.env` 凭据已提交到 Git

`IICtool_v6/.env` 被 `git ls-files` 命中，内容含 `ANTHROPIC_BASE_URL`、**`ANTHROPIC_AUTH_TOKEN`** 等条目。仓库无 `.gitignore`（`git ls-files | grep env` 明确列出 `IICtool_v6/.env`）。

**处置**：立即轮换该 Token → `git rm --cached` → 补 `.gitignore` → 若仓库已推送，需重写历史（`git filter-repo`）并通知所有克隆者。仅删除文件不足以消除泄露，历史中仍可检出。

### P0-2 两套 CRC-32 算法并存且结果不同

**位置**：[crc.py:7-25](IICtool_v6/crc.py#L7-L25) vs [mtp_batch_ops.py:526-533](IICtool_v6/mtp_batch_ops.py#L526-L533)
**证据**：见 §4.3 实测数据，n=312 时 `0x7E4F00E5` vs `0x6FBBA47A`。
**影响**：烧录路径（`mtp_batch_ops.py:219`）与读回自检路径（`mtp_batch_ops.py:526`）不可能一致，全流程的 CRC 自洽性验证形同虚设。

**口径已确认（2026-10-10 定稿，2026-10-14 复核）**：以 [crc.py](ocs_2361_python_code/IICtool_v6/crc.py) 的 LSB 优先实现为**唯一权威**；CRC 只计算模板地址 **0~416**，地址 **416~510 直接烧写、不进 CRC**；结果写 507~510 小端。参考实现见 [CRC_Test.py](ocs_2361_python_code/IICtool_v6/CRC_Test.py)（`CRC_ADDR_LIMIT = 416`）。

**处置：✅ 已修复（2026-10-14）**。`crc.py` 保持不动；烧录侧新增 `CRC_ADDR_LIMIT = 416` 并把「烧录清单」与「CRC 输入」拆成两个集合（`burn_addrs` / `crc_addrs`），回读侧内联 MSB 循环替换为 `calculate_crc32_iter()` 且扫描范围对齐到地址 0~415。验收：生产烧录器与 `CRC_Test.py` 主输出同值、端到端烧录 CRC == 回读 `CALCULATED`。详见 **[MTP批量执行分析.md](MTP批量执行分析.md)**。

> ⚠️ 修复时须注意：原 `phys_addrs_sorted` 同时兼任「CRC 输入」与「烧录清单」。若只加 `x < 416` 过滤，会**静默漏烧 416~510 直烧区**——必须拆成两个集合。

### P1-1 `_call_with_timeout` 超时后遗留线程与总线恢复竞争

**位置**：[i2c_comm.py:527-545](IICtool_v6/i2c_comm.py#L527-L545)，调用点 [i2c_comm.py:627](IICtool_v6/i2c_comm.py#L627)、[i2c_comm.py:663](IICtool_v6/i2c_comm.py#L663)

```python
t.join(timeout_ms / 1000.0)
if t.is_alive():
    raise TimeoutError(...)      # ← 线程仍活着，仍在 DLL 内部执行
```

抛出 `TimeoutError` 后，调用方**立即**执行 `_recover_bus_default()`，其中包含 `CloseUsb()` + `OpenUsb()` + `ConfigIICParam()`（[i2c_comm.py:565-580](IICtool_v6/i2c_comm.py#L565-L580)）。此时那个"超时"线程可能仍在使用同一 `usb_index`，导致句柄被并发关闭/重开。这是 native 层竞争，Python 侧无任何防护，可能表现为偶发挂死或数据错乱。

**处置**：超时后不要复用同一 `usb_index`；改为给超时路径加锁/世代号（generation counter），或让恢复流程等待线程真正退出（带界等待 + 放弃句柄而非重开）。

### P1-2 MTP 使能失败被静默吞掉

**位置**：[mtp_ops.py:31-32](IICtool_v6/mtp_ops.py#L31-L32)、[mtp_ops.py:42-43](IICtool_v6/mtp_ops.py#L42-L43)

```python
def open_mtp_en(self):
    try:
        ...三次关键写入...
    except Exception as e:
        self.log(f"!! Open MTP EN 失败: {e}")     # 只记日志，不抛出
```

GUI 侧的包装（[IICtool.py:533-536](IICtool_v6/IICtool.py#L533-L536)）依赖异常来弹错误框，但异常永远不会到达 → 用户点了「Open MTP EN」，无论成功失败都只看得到 normal 流程，`messagebox.showerror` 是死分支。

**影响**：使能失败后继续烧录，全部写入无效，但流程会一直走到校验阶段才报错（甚至因 P1-3 而不报错）。这是 MTP 操作链上最关键的一步，恰恰是唯一吞异常的。

**处置**：删除 `except`，让异常传播到 GUI；或改为返回 `(success, err)` 并让 `do_mtp_open_en` 检查。

### P1-3 读取失败被静默记为 `0x00`

**位置**：[mtp_batch_ops.py:344-347](IICtool_v6/mtp_batch_ops.py#L344-L347)、[mtp_batch_ops.py:487-490](IICtool_v6/mtp_batch_ops.py#L487-L490)、[mtp_batch_ops.py:407](IICtool_v6/mtp_batch_ops.py#L407)

```python
v0 = mtp_ctrl.read_byte(phys_addr)
b0 = v0[3] if v0 else 0      # 读失败 → 数据 0x00，与"芯片里真是 0"无法区分
```

`read_byte` 本身也已吞异常并返回 `None`（[mtp_ops.py:88-90](IICtool_v6/mtp_ops.py#L88-L90)），于是「读取失败」在导出报表中表现为「该字节为 `00`」。

**影响**：读回数据不可信；坏点被淹没在正常数据里。对烧录校验这种场景是致命的（`verify_mtp_burn` 尚能区分，因为它走的是另一条判断路径）。
**处置**：读失败写空值或 `ERR` 标记，并计入失败计数，由调用方决定是否中止。

### P1-4 扇区导出的 INDEX 列与实际读取位置不自洽

**位置**：[mtp_batch_ops.py:419-435](IICtool_v6/mtp_batch_ops.py#L419-L435)

实际读取的物理字节地址是 `range(sector*32, sector*32+32)`（第 405-408 行），但导出的表格 INDEX 列写的是：

```python
base_mtp_addr = sector << 5                        # = sector * 32
addr_base, index_base = mtp_ctrl._addr_index_from_mtp(base_mtp_addr)   # 字节粒度模型 A
idx_mod = (index_base + w) & 0x3F                  # w = 0..7
```

而模板导入侧的物理地址公式是 `phys = ADDR + INDEX*4`（模型 B，第 141 行）。

**数值反例**（sector = 1）：

| 项 | 值 |
|---|---|
| 实际读取的物理字节 | 32 ~ 63 |
| 代码写出的 INDEX 列 | 32, 33, …, 39（`index_base = _addr_index_from_mtp(32) = 32`） |
| 按模板公式反推 | `0 + 32*4 = 128 ~ 156` ❌ |
| 正确值（模型 B） | `ADDR=0, INDEX=8~15` → `8*4 = 32` ✅ |

**影响**：「读本扇区并导出」导出的文件若重新导入执行，会操作完全不同的地址区间。
**处置**：统一地址模型。导出侧应写 `index_mod = (sector*32 + w*4 - addr_base*64) / 4` 之类的模型 B 表达，或直接把导出列定义为"物理地址"而非"Word 偏移"。

### P1-5 后台线程直接操作 Tk 控件

**位置**：[IICtool.py:273-311](IICtool_v6/IICtool.py#L273-L311)

`trigger_spi_sck_direct` 起一个 daemon 线程，线程内部一路调用 `self.log(...)`，而 `log()` 会执行 `self.log_text.configure()/insert()/yview()`（[IICtool.py:169-178](IICtool_v6/IICtool.py#L169-L178)）。

Tkinter 不是线程安全的，从非主线程操作控件是未定义行为，可能随机崩溃或界面冻结。

**处置**：线程内只往 `queue.Queue` 投递，主线程用 `root.after(50, drain)` 消费。

### P1-6 长任务占用主线程并靠 `update()` 泵消息

**位置**：[IICtool.py:638-644](IICtool_v6/IICtool.py#L638-L644)、[658-664](IICtool_v6/IICtool.py#L658-L664)、[696-700](IICtool_v6/IICtool.py#L696-L700)、[769-773](IICtool_v6/IICtool.py#L769-L773)

烧录/校验/批量读回都在主线程同步执行，靠 `progress_win.update()` 刷新进度条。`update()` 会重新进入事件循环，凡是已排队的回调（例如 P1-5 的后台线程投递、或 `after` 任务）都会在耗时循环**中途**执行，此时 `self.i2c` / `self.mtp` 可能正处于半初始化状态。

配合 P1-5 的线程后门，这条路径存在真实的重入风险。

**处置**：改为工作线程 + `queue` + 主线程 `after` 轮询，彻底去掉 `update()`。

### P1-7 配置文件路径依赖当前工作目录

**位置**：[utils.py:4](IICtool_v6/utils.py#L4)

```python
CONFIG_FILE = "i2c_config.json"     # 相对路径，取决于 CWD
```

打包成 exe 后，若用户从快捷方式、任务栏或"以管理员身份运行"启动，CWD 可能不是 exe 所在目录 → 读不到配置（静默回落默认值）或把配置写到别处。

对比：`i2c_comm._find_dll_path()` 已正确处理（用了 `sys._MEIPASS`，[i2c_comm.py:75-88](IICtool_v6/i2c_comm.py#L75-L88)）。同一份代码里两种做法并存。

另外仓库存放了 **4 份** `i2c_config.json`（根目录、`2361_MTP/`、`2361_MTP/IICtool_v6/`、`IICtool_v6/`），内容各不相同（`COM13` / `COM18`……），极易误改。

**处置**：统一用 `os.path.dirname(sys.executable if frozen else __file__)` 作为基准目录；清理多余副本。

### P1-8 全片校验的 I/O 与日志放大

**位置**：[mtp_batch_ops.py:262-277](IICtool_v6/mtp_batch_ops.py#L262-L277)

- 每个字节调用一次 `log_cb` → 511 行 Tk Text 插入 + 511 条 `log_records`（导出日志 Excel 时一并落盘）
- 每个字节调用一次 `read_byte`，而 `read_byte` = **1 次触发写 + 1 次 4 字节读**（[mtp_ops.py:69-87](IICtool_v6/mtp_ops.py#L69-L87)）

512 字节全片校验 ≈ **1000+ 次 I2C 事务 + 512 次 GUI 更新**。在 100k 速率下这是分钟级等待，且用户无法取消、界面无响应。

**处置**：逐字节日志降级为「每 N 条或每扇区一条」；校验按 4 字节成组读（一个 word 覆盖 4 个校验字节），I2C 事务数直接降到 1/4。

## 八、设计亮点（值得保留）

1. **回调注入解耦彻底**。`MTPBatchLogic` 全静态 + 回调参数，不依赖 Tk 也不依赖具体硬件，可被 CLI 或自动化测试直接复用。这是全库最好的设计决策，重构时应以它为模板推广。
2. **分层边界清晰**，依赖严格单向，无循环引用。
3. **总线自恢复**。读超时自动 `_recover_bus_default`（[i2c_comm.py:547-586](IICtool_v6/i2c_comm.py#L547-L586)），并提供「主动拉高/恢复死锁」手动入口。
4. **无控制台 exe 的启动异常落盘**（[IICtool.py:795-807](IICtool_v6/IICtool.py#L795-L807)）—— 对 GUI 型 exe 现场排障很实用。
5. **DLL 路径多候选查找**（`sys._MEIPASS` → exe 目录 → CWD → `_internal`，[i2c_comm.py:75-88](IICtool_v6/i2c_comm.py#L75-L88)），兼容 onefile/onedir 两种打包形态。
6. **Excel 工作流设计完整**：模板生成 → 填写 → 批量执行 → 读回覆盖，且支持 `START`/`END` 区间标记与 `#` 注释行（[iic_ops.py:320-341](IICtool_v6/iic_ops.py#L320-L341)）。
