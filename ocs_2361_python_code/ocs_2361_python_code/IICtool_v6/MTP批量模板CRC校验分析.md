# MTP 批量模板 CRC 校验分析

> 分析对象：MTP 批量模板中各地址数据参与 CRC 校验的**完整口径**
> 相关文件：[crc.py](crc.py)（算法）、[mtp_batch_ops.py](mtp_batch_ops.py)（烧录/回读两处调用点）、[IICtool.py](IICtool.py)（GUI 触发）
> 结论性质：本报告的算法差异与场景仿真结论均**经实际运行验证**（脚本见附录 C）

## ⚑ 已定口径（2026-10-10 定稿）

**决策一：算法以 [crc.py](crc.py) 的 `calculate_crc32_iter` 为唯一权威口径。**
（`poly=0x04C11DB7`, `init=0xFFFFFFFF`, LSB 优先, `xorout=0`）

**决策二：范围 = 只计入 `ADDR + INDEX*4 < 416` 的行**（即 `phys < 416`，数据区上限为地址 415）。
`phys >= 416` 的行**仍会被烧录，但不参与 CRC**。

```python
# 烧录侧 mtp_batch_ops.py:216 现为「全部 PROGRAM 声明集合」，不含该上限 —— 需加过滤：
data_to_crc = bytes(buffer[x] for x in phys_addrs_sorted)
#   → 应改为先按行过滤：phys_addrs_sorted = sorted(x for x in phys_addrs_set if x < 416)
# 回读导出侧 mtp_batch_ops.py:526-533 用的是内联 MSB 循环 + 固定 INDEX 1..78，
# 算法与范围都与烧录侧不一致，两处都要改：
crc, _ = calculate_crc32_iter(bytes(read_buffer))     # ← 改为按 crc.py
```

**实测验证**（工具 [CRC_Test.py](CRC_Test.py)，与生产函数逐值交叉核对）：

| 文件 | 计入 CRC 的行 | 字节数 / 地址 | **CRC32（确认值）** | 模板行中声明 | 结论 |
|---|---|:---:|---|---|---|
| `MTP_配置寄存器V0.7（测试版本).xlsx`（用户现场文件） | 第 3~84 行 | 328 / 4~415 | **`0x2ACAFA84`** | 第 93 行 `0x0F348CFA` | 声明值是**旧值** |
| `MTP_配置寄存器V0.7（正常版本）.xlsx` | 第 3~84 行 | 328 / 4~415 | **`0xFA261297`** | 第 86 行 `0x0F348CFA` | 声明值是**旧值** |

两份模板的字面差异只有一处数据：`G57` = `5E`（正常版）vs `1E`（测试版），因此 CRC 不同；
而两份模板的 CRC 行却写着**同一个** `0x0F348CFA` —— 这印证了该声明值是**沿用的旧值**，
并非由各自的数据算出。**模板中的 CRC 行应更新为上表对应值。**

> 口径演进记录（供追溯）：`phys < 408` → `0x77A93095` / `0x34457A0C`（差额恰为第 83、84 行，
> `phys = 408 / 412`）。用户最终确认 **上限为 416**，即地址 **4~415** 全部计入。
> 工具中以 `CRC_ADDR_LIMIT = 416` 实现，改一行即可切换。

### ⚠️ 与现场控制台 `crc 4 506` 的关系（重要）

`tests.py` 的 `crc <lo> <hi>` 命令与 `使用教程.md` 示例用的是 **4~506 全区间**读回再算 CRC：

```
MTP> crc 4 506
   ✅ CRC32(地址 4~506，503 字节) = 0x0F348CFA
```

这是**烧录后对芯片做整体完整性复核**的用法，与"由模板数据算出待写入的 CRC"**不是同一件事**：

- 烧录口径（决策二）= **首个空行之前的 PROGRAM 声明集合**（如 328 字节）；
- 复核口径 = **4~506 连续的 503 字节**，其中未被模板声明的字节取决于芯片实际内容。

因此**二者只有在模板完整覆盖 4~506 时才会得到同一个值**。本模板只声明了 352 / 503
字节，若按 4~506 + 未定义按擦除态 `0xFF` 推算得 `0x81DF4FD7`，与 `0x2ACAFA84` 不同。
→ 用 `crc 4 506` 复核本模板烧录结果时，**不能拿 `0x2ACAFA84` 当期望值**。

## 〇、结论摘要（TL;DR）

| # | 结论 | 严重度 | 验证方式 |
|---|---|:---:|---|
| **1** | **烧录与回读使用了两套不等价的 CRC 算法**。烧录走 [crc.py](crc.py)（逐字节 LSB 优先），回读导出走 [mtp_batch_ops.py:526](mtp_batch_ops.py#L526) 内联循环（逐字节 MSB 优先）。二者**仅当所有输入字节都是"位回文"时才相等**，真实数据必然不等。 | 🔴 **致命** | 实测，见第三章 |
| **2** | 因此导出的 `CALCULATED(本次数据算得的新CRC)` **永远不等于** `PROGRAM(存储的CRC)`，**CRC 校验锚点当前完全失效**。 | 🔴 **致命** | 场景 A 实测 |
| **3** | 两算法的 CRC **输入字节流完全一致**（都等价于字节 4~315 的升序镜像，前提是模板填满），差异**纯粹来自算法**，与地址覆盖无关。 | — | 场景 A 实测 |
| **4** | 烧录侧覆盖范围 = "首个空行之前的 PROGRAM 声明集合"（已确认为**权威口径**），回读侧 = "固定连续的 4~315"。**模板一旦有空洞或超出 315，两口径必然对不上**，这是第二类独立缺陷。 | 🟠 高 | 场景 B / C 实测 |
| **5** | `crc_end=506` 的上界与"CRC 保留区 507~510"存在重叠风险：模板若写到 INDEX 126（字节 504~507），会污染 CRC 输入流。 | 🟡 中 | 静态分析 |
| **6** | inline 实现 = **标准 CRC-32/MPEG-2**（校验值 `"123456789" → 0x0376E6E7` 实测吻合）；`crc.py` = 标准算法作用于**逐字节位反转后**的数据，**不是**标准 MPEG-2。 | — | 实测，见第三章 |

**一句话**：算法上 `crc.py` 与导出内联循环不是同一个算法，**已定以 `crc.py` 为准**；范围上**已定以「`ADDR + INDEX*4 < 416` 的行」为准**（地址 4~415）。两处必须同时落实到烧录侧与回读导出侧，否则算出的 CRC 依然对不上。

## 一、模板地址 → MTP 字节地址映射

模板列定义（[mtp_batch_ops.py:126](mtp_batch_ops.py#L126)）：

| 列 | 表头 | 含义 |
|---|---|---|
| A | OPERATION | `READ` / `PROGRAM` / `ERASE_SECTOR` |
| B | ADDR(基地址) | 0~511（模板默认 0） |
| C | INDEX(Word偏移) | 1 代表偏 4 字节 |
| D | [31:24] | 物理地址 `ADDR+INDEX*4 + 3` |
| E | [23:16] | `+2` |
| F | [15:8] | `+1` |
| G | [7:0] | `+0` |
| H | 物理地址(计算) | 公式 `=B{row}+C{row}*4` |

**核心换算**（烧录侧 [mtp_batch_ops.py:191](mtp_batch_ops.py#L191)，回读侧 [mtp_batch_ops.py:479](mtp_batch_ops.py#L479)，两侧一致）：

```python
phys_addr = ADDR + INDEX * 4          # 得到一个"字起始字节地址"
```

**4 字节的落位**（[mtp_batch_ops.py:198-201](mtp_batch_ops.py#L198-L201)）：

```
buffer[phys_addr + 0] = [7:0]      ← 低字节落在低地址
buffer[phys_addr + 1] = [15:8]
buffer[phys_addr + 2] = [23:16]
buffer[phys_addr + 3] = [31:24]    ← 高字节落在高地址
```

即 **32 位字在小端字节序下铺进 MTP 地址空间**。

### 标准模板（`generate_mtp_template`，ADDR=0，INDEX 1~78）

| Excel 行 | INDEX | 物理地址 phys | 覆盖字节区间 |
|:---:|:---:|:---:|---|
| 3 | 1 | 4 | 4 ~ 7 |
| 4 | 2 | 8 | 8 ~ 11 |
| 5 | 3 | 12 | 12 ~ 15 |
| … | … | … | … |
| 79 | 77 | 308 | 308 ~ 311 |
| 80 | 78 | 312 | 312 ~ 315 |

- 行数：`range(1, 79)` → 78 行（[mtp_batch_ops.py:140](mtp_batch_ops.py#L140)）
- 覆盖字节：**4 ~ 315，共 312 字节**
- **字节 0~3 永不出现**（模板从 INDEX=1 起，跳过 INDEX=0）

## 二、CRC 覆盖范围分析

### 2.1 三条相关流程的 CRC 口径对比

| 维度 | ①全片烧录（写 CRC） | ②读出并导出（算 CRC） | 差异 |
|---|---|---|---|
| 入口方法 | `mtp_full_program_with_crc_gui` [:161](mtp_batch_ops.py#L161) | `read_mtp_and_export_template` [:442](mtp_batch_ops.py#L442) | — |
| **输入字节流** | `phys_addrs_sorted` 按**升序**逐字节取 `buffer[x]` [:216](mtp_batch_ops.py#L216) | `read_buffer` 按 INDEX=1→78 **升序** extend `[b0,b1,b2,b3]` [:491](mtp_batch_ops.py#L491) | 填满模板时**相同** |
| **输入来源** | Excel 声明为 `PROGRAM` 的地址集合 | **固定** `INDEX 1..78`（硬编码） | 有空洞/越界时**不同** |
| **算法** | `calculate_crc32_iter`（[crc.py](crc.py)，**LSB 优先**）[:219](mtp_batch_ops.py#L219) | 内联循环（**MSB 优先**）[:526-533](mtp_batch_ops.py#L526-L533) | 🔴 **不同** |
| 初值 / 多项式 | `0xFFFFFFFF` / `0x04C11DB7` | 同 | 相同 |
| 结果用途 | 写入字节 507~510（小端） | 追加 `CALCULATED` 行供人工比对 | — |

### 2.2 512 字节地址空间的保护状态

```
字节地址  0        4                                    315      507  511
          ├────────┼────────────────────────────────────┤          ├───┤
          │ 未保护 │        CRC 数据区（312 B）          │  未保护   │CRC│
          │  INDEX0│    INDEX 1 … 78（ADDR=0）          │ 316~506  │区 │
          └────────┴────────────────────────────────────┘          └───┘
```

| 区间 | 字节数 | 是否进 CRC | 说明 |
|---|---:|---|---|
| 0 ~ 3 | 4 | ❌ 否 | 模板不含 INDEX=0；`crc_start` 被强制 `max(4, …)` [:212](mtp_batch_ops.py#L212) |
| **4 ~ 315** | **312** | ✅ 是 | 标准模板的全部数据区 |
| 316 ~ 506 | 191 | ⚠️ 视模板而定 | 回读流程**永不**纳入；烧录流程**只要模板声明了就纳入** → 口径分裂 |
| 507 ~ 510 | 4 | ❌ 否（作为数据） | CRC 保留区，小端存放 [:220-223](mtp_batch_ops.py#L220-L223) |
| 511 | 1 | ❌ 否 | 未使用；且模板写到 509~511 会触发越界（见第五章） |

### 2.3 CRC 数据区的扇区分布

`sector = byte_addr >> 5`，数据区 4~315 横跨 **10 个扇区（0~9）**：

| 扇区 | 字节区间 | 纳入 CRC 的字节 | 数量 |
|:---:|---|---|---:|
| 0 | 0 ~ 31 | 4 ~ 31 | 28 |
| 1 | 32 ~ 63 | 32 ~ 63 | 32 |
| 2 | 64 ~ 95 | 64 ~ 95 | 32 |
| 3 | 96 ~ 127 | 96 ~ 127 | 32 |
| 4 | 128 ~ 159 | 128 ~ 159 | 32 |
| 5 | 160 ~ 191 | 160 ~ 191 | 32 |
| 6 | 192 ~ 223 | 192 ~ 223 | 32 |
| 7 | 224 ~ 255 | 224 ~ 255 | 32 |
| 8 | 256 ~ 287 | 256 ~ 287 | 32 |
| 9 | 288 ~ 319 | 288 ~ 315 | 28 |
| | | **合计** | **312** |

→ 数据区**首尾各截断一个扇区**（扇区 0 的前 4 字节、扇区 9 的后 4 字节被排除）。这意味着按扇区粒度做"部分重烧"时，边界扇区无法与其 CRC 自洽。

## 三、两处 CRC 实现的算法鉴定（实测）

### 3.1 源码对照

```python
# A. crc.py:16-24  —— 烧录流程使用
for idx, b in enumerate(data):
    for i in range(8):                      # i = 0..7 → 先取 bit0（LSB 优先）
        bit = (b >> i) & 1
        a = ((crc >> 31) & 1) ^ bit
        crc = (crc << 1) & 0xFFFFFFFF
        if a: crc ^= poly

# B. mtp_batch_ops.py:526-533 —— 回读导出流程使用
for byte in read_buffer:
    crc ^= (byte << 24)                     # 整字节异或进高 8 位 → 先溢出 bit7（MSB 优先）
    for _ in range(8):
        crc = ((crc << 1) ^ 0x04C11DB7) & 0xFFFFFFFF if crc & 0x80000000 else (crc << 1) & 0xFFFFFFFF
```

A 逐位取 **bit0→bit7**，B 通过 `byte << 24` 使 **bit7→bit0** 先参与移位。两者对同一字节的位处理顺序相反。

### 3.2 单字节实测结果

| 输入字节 | 是否位回文 | `crc.py`（A，烧录） | 内联（B，回读） | 结果 |
|:---:|:---:|---|---|:---:|
| `0x00` | ✅ | `0x4E08BFB4` | `0x4E08BFB4` | 相同 |
| `0x01` | ❌ | `0x27045F5A` | `0x4AC9A203` | **不同** |
| `0x02` | ❌ | `0x7A8ECFC3` | `0x478A84DA` | **不同** |
| `0x08` | ❌ | `0x021964C4` | `0x6800520C` | **不同** |
| `0x80` | ❌ | `0x4AC9A203` | `0x27045F5A` | **不同**（与 0x01 恰好互换） |
| `0xFF` | ✅ | `0xFFFFFF00` | `0xFFFFFF00` | 相同 |
| `0xA5` | ✅ | `0xA8E282D1` | `0xA8E282D1` | 相同 |
| `0x5A` | ✅ | `0x1915C265` | `0x1915C265` | 相同 |
| `0x81` | ✅ | `0x23C542ED` | `0x23C542ED` | 相同 |
| `0x42` | ✅ | `0x730CF4AD` | `0x730CF4AD` | 相同 |
| `0x24` | ✅ | `0xC52F7F88` | `0xC52F7F88` | 相同 |

**规律**：若字节满足 `bit_reverse8(b) == b`（位回文：`0x00 0x11?` 注意 `0x11` 反转仍是 `0x11`？——`0x11=00010001`→`10001000=0x88`，非回文；实际回文集为 `00, FF, 81, 42, 24, 18, 3C, 66, 99, C3, A5, 5A, E7, 7E, BD, DB` 等），则两算法给出**相同**结果；否则不同。

### 3.3 两算法的精确关系（实测 200 组随机数据 100% 成立）

$$\texttt{crc.py}\big(\,\{\text{rev8}(b)\ \mid\ b \in \text{data}\}\,\big) \;=\; \texttt{inline}(\text{data})$$

即 **`crc.py` 等价于"先把每个字节做 8 位位反转，再走标准算法"**。

### 3.4 标准向量交叉验证

| 计算 | 结果 |
|---|---|
| 已知标准值 CRC-32/MPEG-2(`"123456789"`) | `0x0376E6E7` |
| **inline（回读侧）** `123456789` | **`0x0376E6E7`** ✅ 完全吻合 |
| `crc.py`（`123456789` 逐字节 rev8 后） | `0x0376E6E7` ✅ |
| `crc.py`（`123456789` 原样） | `0x9B63D02C` ❌ 非标准 |

**判定**：
- **回读侧内联循环 = 标准 CRC-32/MPEG-2**
- **`crc.py` = 标准 MPEG-2 作用于位反转字节流**，虽在轮询/逐字节中间结果上设计得较完整，但**不是**设备通行的 MPEG-2 口径

## 四、场景仿真：什么时候会对不上

### 4.1 四类场景实测

仿真条件：512 字节镜像填充 `byte = index & 0xFF`；模拟两侧的真实输入流与算法。

| 场景 | 烧录 CRC（`crc.py`，集合=Excel 声明） | 回读 CRC（**修复前** inline，集合=固定 4~315） | 判定（修复前） |
|---|---|---|---|
| **A** 标准模板 78 行全填，字节 4~315 | `0x4D1D7A77`（312 B） | `0x61FF70B5`（312 B） | 🔴 **对不上** — 输入流相同，**纯算法差异** |
| **B** 模板有空洞（仅 INDEX 1-3、10-12） | `0x08A50325`（24 B） | `0x61FF70B5`（312 B） | 🔴 对不上 — **算法 + 覆盖** 双重差异 |
| **C** 模板多写到 INDEX 79~126（字节 316~507） | `0xD7DF1BCC`（504 B） | `0x61FF70B5`（312 B） | 🔴 对不上 — **算法 + 覆盖** 双重差异 |
| **D** 全 `0xFF`（回文字节） | `0x1BE4E76F` | `0x1BE4E76F` | ⚪ **巧合一致** — 回文字节使两算法退化为同一结果 |

> **场景 D 为什么危险**：MTP 擦除后通常为全 `0xFF`，或某些测试数据恰好只用 `0x00/0xFF/0x5A/0xA5` 等回文字节。这类数据下两算法**恰好给出相同 CRC**，校验"看起来通过"，从而**掩盖了算法缺陷**，直到换成真实业务数据才暴露。这是该缺陷能以现状留存至今的合理解释。

### 4.3 修复后效果（以 crc.py 为准，回读侧改为 `calculate_crc32_iter`）

| 场景 | 烧录 CRC（`crc.py`） | 回读 CRC（**修复后** `crc.py`） | 判定（修复后） |
|---|---|---|---|
| **A** 标准模板 78 行全填，字节 4~315 | `0x4D1D7A77`（312 B） | `0x4D1D7A77`（312 B） | ✅ **一致** — 算法统一后锚点恢复可用 |
| **B** 模板有空洞（仅 INDEX 1-3、10-12） | `0x08A50325`（24 B） | `0x4D1D7A77`（312 B） | 🔴 **仍对不上** — 残留的**覆盖**差异（P-CRC-2 未解决） |
| **C** 模板多写到 INDEX 79~126（字节 316~507） | `0xD7DF1BCC`（504 B） | `0x4D1D7A77`（312 B） | 🔴 **仍对不上** — 残留的**覆盖**差异（P-CRC-2 未解决） |
| **D** 全 `0xFF`（回文字节） | `0x1BE4E76F` | `0x1BE4E76F` | ✅ 一致 |

> **读法**：以 `crc.py` 为准只消除**算法**差异（场景 A 由 🔴 转 ✅）。**只要模板不是"INDEX 1~78 连续填满且全为 PROGRAM"，烧录与回读的 CRC 仍然对不上**——因为烧录算的是 Excel 声明集合、回读算的是固定 4~315。因此 P-CRC-2（统一为固定区间 + 模板完整性校验）必须在同一批修改中一并落地，否则修复不完整。
>
> 唯一无需额外处理的场景是 D（回文字节），它在修复前后都一致——但其"一致"本身不构成验证依据。

### 4.4 字节序核对（显示层无误）

CRC 落盘为**小端**：`[507]=crc&0xFF, [508]=crc>>8, [509]=crc>>16, [510]=crc>>24`。

以修复前的回读值 `0x61FF70B5` 为例：

```
存储: [507]=B5  [508]=70  [509]=FF  [510]=61
导出: [31:24]=61 [23:16]=FF [15:8]=70 [7:0]=B5  →  显示 0x61FF70B5   ✅ 正确
```

→ **存储与显示的字序均正确**，两侧比较是"同一字序下的公平比较"，问题**仅**出在算法本身与覆盖集合上。

## 五、CRC 保留区与地址重叠风险

### 5.1 越界：模板写到物理地址 509~511 必崩

[mtp_batch_ops.py:192-201](mtp_batch_ops.py#L192-L201)：

```python
if phys_addr < 0 or phys_addr > 511: continue    # 511 会被放行
...
buffer[phys_addr + 3] = b31                      # buffer[514] → IndexError
```

`bytearray(512)` 合法下标 0~511，故 `phys_addr ∈ {509, 510, 511}` 必然抛 `IndexError`。异常被外层捕获后返回 `"bytearray index out of range"`，**不指向具体 Excel 行**。

对应模板含义：`INDEX = 127`（phys = 508）尚可，`INDEX ≥ 128`（phys ≥ 512）被跳过，而 **509~511 处于"既不跳过也不越界"的缝隙区间**。

### 5.2 污染：写入 507~510 会改变 CRC 输入流

烧录流程的赋值顺序（[:215-223](mtp_batch_ops.py#L215-L223)）：

```python
data_to_crc = bytes(buffer[x] for x in phys_addrs_sorted)   # ① 此时 507 还是 Excel 的值
final_crc, _ = calculate_crc32_iter(data_to_crc)
buffer[507] = final_crc & 0xFF                              # ② 再被 CRC 覆盖
```

若 Excel 声明了 `INDEX = 126`（phys = 504，覆盖 504~507），则：

- 字节 507 的 **Excel 值先进入 CRC 输入流**；
- 随后 **被 CRC 字节覆盖**，设备上最终不存在该 Excel 值；
- 该 CRC 因此**不可能**被任何读回数据复现——因为输入流中有一个字节"烧完之后就没了"。

同时 `phys_addrs_sorted` 含 507，而 [:244](mtp_batch_ops.py#L244) 的 `range(507, 511)` 也会写 507 → **同一字节在同一遍内被 `program_byte` 写两次**（值相同，无实际危害，但写入计数与耗时统计偏高）。

### 5.3 上界 `crc_end = 506` 的两难

[:213](mtp_batch_ops.py#L213) 把 `crc_end` 夹到 506，意在"CRC 数据区不侵犯 507~510 保留区"。但：

- 该夹取**仅在 `phys_addrs_sorted` 为空时生效**（[:207-218](mtp_batch_ops.py#L207-L218)）；
- 正常路径下用的是 `phys_addrs_sorted`，**完全绕过** 506 这个上界。

→ 保留区的保护形同虚设。

## 六、问题清单与修复建议

### 🔴 P-CRC-1 两处 CRC 算法不等价（致命）— **已定口径：以 crc.py 为准**

**现象**：烧录写入 `crc.py` 口径的 CRC，回读导出用标准 MPEG-2 口径计算并展示，两者对真实数据必然不等 → 校验锚点失效。

**已采纳的修复（唯一方案，用户已确认以 [crc.py](crc.py) 为准）**：

`crc.py` **保持不变**；只改**回读导出侧**，把内联 MSB 循环替换为对 `calculate_crc32_iter` 的调用。

```python
# —— 修改前  mtp_batch_ops.py:526-533（MSB 优先，与 crc.py 不等价）——
crc = 0xFFFFFFFF
for byte in read_buffer:
    crc ^= (byte << 24)
    for _ in range(8):
        crc = ((crc << 1) ^ 0x04C11DB7) & 0xFFFFFFFF if crc & 0x80000000 else (crc << 1) & 0xFFFFFFFF

# —— 修改后（以 crc.py 为准）——
crc, _ = calculate_crc32_iter(bytes(read_buffer))
```

- `calculate_crc32_iter` 在 [mtp_batch_ops.py:6](mtp_batch_ops.py#L6) **已导入**，无需新增 import；
- 改动点仅一处（[mtp_batch_ops.py:526-533](mtp_batch_ops.py#L526-L533)）；内联循环若无其他引用方可直接删除；
- **不改变烧录写入芯片的 CRC 值**（烧录侧本就用 `crc.py`），因此**不影响在途批次**，无需量产评估。

> ~~方案 1（改 `crc.py` 为 MSB 优先）~~ / ~~方案 3（烧录侧对字节 rev8）~~：**均已否决**。两者都会改变写入芯片的 CRC 值，而采取"以 `crc.py` 为准"后，设备侧既有数据的 CRC 口径不变。

**⚠️ 本项修复不覆盖 P-CRC-2**：算法统一后，模板若有空洞或超出 315，两侧 CRC 仍对不上（见 §4.3）。两项应在同一批修改中一起落地。

### 🔴 P-CRC-2 输入集合口径分裂（高）

**现象**：烧录按"Excel 声明集合"，回读按"固定 4~315"。

**修复建议**：

```python
# 在 mtp_full_program_with_crc_gui 中，把 CRC 输入统一改为固定区间，
# 并显式校验模板恰好覆盖 4~315 且无空洞/无越界，否则直接拒绝并提示行号：
expected = set(range(4, 316))
declared = set(phys_addrs_set)
if declared != expected:
    missing = sorted(expected - declared)[:10]
    extra   = sorted(declared - expected)[:10]
    return False, None, None, None, (
        f"模板覆盖不完整，无法与回读口径对齐。\n缺失字节(前10): {missing}\n多余字节(前10): {extra}")
```

**操作层规避**（当前版本即可用）：**模板必须从 INDEX=1 连续填到 INDEX=78，不多不少**，且所有行均为 `PROGRAM`。

### 🟡 P-CRC-3 保留区重叠与 507 字段被覆盖（中）

**修复建议**：在 `data_to_crc` 之前先把 CRC 区置为占位值，或明确排除：

```python
for off in range(507, 511):
    buffer[off] = 0x00                     # 或 0xFF，固定占位，使 CRC 可复现
phys_addrs_sorted = [x for x in phys_addrs_sorted if x < 507]   # 数据区与保留区解耦
```

### 🟡 P-CRC-4 `phys_addr > 508` 应拒绝而非越界（中）

```python
if not (0 <= phys_addr <= 508):            # 508+3 = 511 为合法上界
    continue                               # 并 log 出 Excel 行号，便于排查
```

### 🟢 P-CRC-5 CRC 覆盖区间不可配置（低）

`crc_start` / `crc_end` 既无 GUI 控件（[IICtool.py:43-44](IICtool.py#L43-L44) 只定义了 `StringVar`），正常路径又被 `phys_addrs_sorted` 覆盖 → 应删除或在 GUI 真正接线。

### 🟢 P-CRC-6 中间结果未使用（低）

`calculate_crc32_iter` 返回的 `iter_results`（逐字节中间 CRC）**无任何调用方**，属历史遗留。

| 使用场景 | 修复前能否依赖 CRC | 修复后能否依赖 CRC | 说明 |
|---|:---:|:---:|---|
| 标准模板 78 行全填 + 真实业务数据 | ❌ | ✅ | 修复前算法不等价；以 `crc.py` 为准统一回读侧后锚点恢复 |

> **关键澄清**：`verify_mtp_burn`（[mtp_batch_ops.py:250](mtp_batch_ops.py#L250)）不校验 CRC 值的正确性——它把 CRC 字节也当成普通数据与 `buffer` 比较。所以"全片擦写+校验"**报告的通过只代表写入落位正确，不代表 CRC 正确**。真正想用 CRC 判定内容完整性，只能走"读出MTP并导出"并人工比对两行——修复前这条路被 P-CRC-1 阻断。

## 附录 B：CRC 输入流构造要点

1. **取数顺序**：按**字节地址升序** 4, 5, 6, …, 315（不是按 32 位字取值）。
2. **字内顺序**：小端铺放 → 低地址存低字节（`[7:0]`），高地址存高字节（`[31:24]`）。
3. **单位**：CRC 的输入单位是**字节**（312 B），初值 `0xFFFFFFFF`，多项式 `0x04C11DB7`，**无最终异或**（`xorout = 0`）。
4. **回读等价性**：导出模板的每行 `PROGRAM` 恢复出的字节镜像与原模板**完全一致**（可无损再烧录），这是该模板设计上的正确之处。

### C.2 内联自检脚本（复现本报告结论）

放进 `IICtool_v6/` 直接运行，可复现本报告全部实测结论：

```python
# -*- coding: utf-8 -*-
"""MTP 模板 CRC 一致性自检：验证烧录侧与回读侧算法是否等价。"""
from crc import calculate_crc32_iter

def inline_crc(data):                      # mtp_batch_ops.py:526-533 的回读侧实现
    crc = 0xFFFFFFFF
    for byte in data:
        crc ^= (byte << 24)
        for _ in range(8):
            crc = ((crc << 1) ^ 0x04C11DB7) & 0xFFFFFFFF if crc & 0x80000000 else (crc << 1) & 0xFFFFFFFF
    return crc

def rev8(b):
    r = 0
    for _ in range(8):
        r = (r << 1) | (b & 1); b >>= 1
    return r

# 1) 标准向量：证明 inline 是标准 CRC-32/MPEG-2
assert inline_crc(b"123456789") == 0x0376E6E7, "inline 不是标准 MPEG-2"
print("inline == 标准 CRC-32/MPEG-2 : OK")

# 2) 关系式：crc.py(逐字节 rev8) == inline
d = bytes(range(32))
assert calculate_crc32_iter(bytes(rev8(x) for x in d))[0] == inline_crc(d)
print("crc.py(rev8(data)) == inline(data) : OK")

# 3) 口径差异：真实数据下必然不等 → 校验锚点失效
buf = bytearray([i & 0xFF for i in range(512)])
burn = calculate_crc32_iter(bytes(buf[4:316]))[0]      # 烧录侧口径（crc.py）
read = inline_crc(bytes(buf[4:316]))                   # 回读侧口径（修复前 inline）
print(f"烧录侧 CRC = 0x{burn:08X}")
print(f"回读侧 CRC = 0x{read:08X}")
print("=> 一致（锚点可用）" if burn == read else "=> ★不一致：CRC 校验锚点失效，需统一算法")

# 4) 修复后回归：以 crc.py 为准，回读侧改为 calculate_crc32_iter
read_fixed = calculate_crc32_iter(bytes(buf[4:316]))[0]
assert read_fixed == burn, "修复后仍不一致，检查是否漏改覆盖区间"
print(f"修复后回读侧 CRC = 0x{read_fixed:08X}  -> 与烧录侧一致 ✅")
```

预期输出（与第四章场景 A / §4.3 一致）：

```
inline == 标准 CRC-32/MPEG-2 : OK
crc.py(rev8(data)) == inline(data) : OK
烧录侧 CRC = 0x4D1D7A77
回读侧 CRC = 0x61FF70B5
=> ★不一致：CRC 校验锚点失效，需统一算法
修复后回读侧 CRC = 0x4D1D7A77  -> 与烧录侧一致 ✅
```

> 说明：
> - 第 1~3 段用于**复现缺陷**（修复后仍应保持通过，因为 `inline_crc` 是脚本内置的对照实现）；
> - 第 4 段是**修复后的回归断言**，可直接用作改完 `mtp_batch_ops.py` 后的验收依据。
> - 该脚本为**只读验证**，不触碰串口、DLL 与任何文件。
